| Prioridad | Evidencia e impacto | Tratamiento |

| P1 seguridad | `current_profile_role()` devuelve NULL para perfiles ausentes/inactivos. En 21 RPC, `IF role <> ...` o `NOT IN` no entra al rechazo cuando el resultado es NULL. `request_movement_correction` presenta el mismo problema en una condición compuesta. Un JWT válido de un perfil inactivo puede superar el control inicial de privilegios. | Corregidas 22 definiciones mediante migración: `IS DISTINCT FROM`, `coalesce` y `IS NOT TRUE`. Probado rechazo de las 22 en PostgreSQL aislado. La migración aún NO está aplicada. |
| P1 seguridad | Ambas funciones de recuperación comprobaban `used_at` y cambiaban Auth antes de consumir el token. Solicitudes concurrentes podían reutilizar un token válido. | Consumo condicional atómico antes de modificar Auth; solo una solicitud puede continuar. Prueba concurrente por endpoint. Si Auth falla después, se exige un enlace nuevo; no se vuelve a habilitar un token consumido. Fuentes incorporadas al repo; sin despliegue. |
| P1 operación | `refreshSession()` podía ejecutarse varias veces durante `loadAll`; cada consulta detectaba el mismo vencimiento. Además, una renovación en vuelo podía restaurar la sesión tras cerrar. | Promesa compartida, descarte de respuestas de sesiones anteriores y logout sin restaurar credenciales globales. | P1 operación | Compras y alertas convertían errores HTTP en listas vacías mientras el indicador podía decir ACTUALIZADO. | Se conserva la última lectura y se informa DATOS PARCIALES. Prueba de fallo de carga de compras. |

## Controles existentes verificados

- 28 tablas públicas con RLS habilitado; vistas públicas consultadas con `security_invoker=true`.
- RPC sensibles concedidas a `authenticated`, sin ejecución anónima en las funciones operativas inspeccionadas. Los 38 avisos del asesor sobre SECURITY DEFINER requieren inspección de guardas; no son 38 vulnerabilidades automáticamente.
- Storage `purchase-documents` e `inventory-documents` privados. `avh-web` es público para recursos web históricos.
- Operaciones de stock validan depósito mediante `assert_can_access_warehouse`; salidas y transferencias bloquean lotes y usan asignaciones FIFO. Recepción bloquea compra e ítems y rechaza cantidades superiores a pendientes.
- No se detectaron, en las consultas agregadas realizadas, lotes negativos/superiores al recibido, cantidades recibidas fuera de rango ni recepciones con movimiento anulado: 0 / 0 / 0. No se hizo reconciliación contable completa.
- Las funciones IA inspeccionadas validan usuario y perfil activo; la IA del depositario se limita a recepción y comprueba los IDs contra la OC del depósito. Salidas manuales permanecen intactas.
- Cuatro endpoints legacy (`avh-bootstrap`, `avh-publish-static`, `inventario-avh-v2-app`, `inventario-avh-v2-web`) devuelven 410; aparecer ACTIVE en el listado no significa que sigan ejecutando su lógica antigua.
- Despliegue Pages restringido a main; la rama y el PR no publican producción. No se agregó despliegue automático de SQL ni Edge Functions.
