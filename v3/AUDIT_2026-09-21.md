# Auditoría AVH V3 — 2026-09-21

## Alcance y regla de seguridad

Auditoría de frontend V3, GitHub Actions, Supabase/PostgreSQL, RLS, RPC, Storage, Edge Functions y flujos de Compras/Depósito/Inventario.

**Producción se inspeccionó en modo lectura.** No se aplicaron migraciones, no se desplegaron Edge Functions y no se modificaron datos ni configuración de Auth. Las correcciones quedan únicamente en esta rama/PR para revisión.

Base auditada de GitHub: `main` en `51e9c4e92ee6d26ad1439ef3d682cc1c44ddf927`.

## Resumen ejecutivo

La arquitectura V3 está razonablemente bien separada: frontend estático, Supabase Auth, PostgreSQL/RLS como autoridad, RPC para mutaciones sensibles, Storage privado y Edge Functions con service role detrás de autenticación/autorización propia. Las 28 tablas públicas observadas tienen RLS habilitado.

No se encontró una razón para reescribir la aplicación ni para mover reglas críticas al frontend. Sí se encontraron problemas concretos de seguridad y consistencia que conviene cerrar.

### P1 — Alta: referencia de archivos de recepción no estaba ligada a la compra

`register_purchase_receipt_document` validaba rol, recepción y depósito, pero aceptaba `p_file_path` sin comprobar que el archivo perteneciera al expediente de esa compra.

Esto era especialmente sensible porque `purchase-invoice-control-ai` usa service role para descargar el `file_path` guardado. Un usuario con acceso a una recepción podía intentar registrar una ruta conocida de otro expediente y provocar una lectura privilegiada del archivo.

**Corrección incluida:** `20260921172000_receipt_document_path_guard.sql`.

La función ahora:
- exige la ruta `<purchase_id>/receipts/...`;
- comprueba que el objeto exista en el bucket privado `purchase-documents`;
- mantiene las mismas reglas de rol, depósito, auditoría y actualización de factura.

### P1 — Alta: endpoint temporal de reset administrativo

En producción existe `avh-admin-temp-reset` con `verify_jwt=false`. El endpoint se autentica mediante token de recuperación, pero:
- modifica la contraseña mediante una petición GET;
- recibe el token en URL;
- devuelve una contraseña temporal en texto plano en la respuesta.

El token es de un solo uso y se almacena hasheado, lo cual reduce el riesgo, pero el diseño sigue siendo innecesariamente sensible a historial, logs, prefetch y exposición accidental del enlace.

**Corrección incluida:** se versiona `edge-functions/avh-admin-temp-reset/index.ts` como endpoint retirado (`410 Gone`). No fue desplegado a producción.

También se versiona una versión endurecida de `avh-admin-recover` con `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, CSP, protección contra framing y mensajes de error que no exponen detalles internos.

### P1 — Media/Alta: cierre de sesión podía persistir localmente

`signOut()` borraba primero el almacenamiento local, pero luego restauraba temporalmente la sesión para llamar a `/auth/v1/logout`. Si `request()` refrescaba el token durante ese paso, `refreshSession()` podía volver a escribir una sesión en `localStorage` antes del reload.

**Corrección incluida:** el bloque `finally` vuelve a ejecutar `saveSession(null)` antes de recargar, garantizando que el cierre local sea definitivo incluso si hubo refresh.

### P2 — Media: módulo de solicitud de producto para administrador

La UI mostraba al administrador el formulario de “Solicitar producto”, pero el RPC `create_product_request` está diseñado para un depositario activo con depósito asignado. El administrador podía llegar a una acción que el backend rechazaba correctamente.

**Corrección incluida:** administración ve la cola de solicitudes y una indicación de usar Catálogos para altas directas; el formulario/RPC queda solo para depositarios.

## Hallazgos revisados que NO se modifican en este PR

### SECURITY DEFINER

Supabase Advisor marca funciones `SECURITY DEFINER` ejecutables por `authenticated`. Se revisaron las rutas críticas.

- RPC administrativos como `admin_create_purchase`, `admin_update_purchase`, `admin_confirm_purchase`, `admin_void_movement` y gestión de inventario inicial verifican `current_profile_role()='admin'`.
- RPC operativos como `record_entry`, `record_exit`, `record_transfer`, `receive_transfer` y `receive_purchase` validan depósito mediante `assert_can_access_warehouse` o equivalente.
- Las funciones trigger/auditoría internas ya no son ejecutables por `authenticated`.
- No se hace un revoke masivo a `authenticated` porque rompería RPC y funciones auxiliares usadas por RLS.

### `admin_recovery_tokens`

Advisor informa “RLS enabled, no policy”. La tabla no tiene grants para `anon` ni `authenticated`; los grants observados corresponden a `postgres` y `service_role`. En este caso la ausencia de policy de usuario es intencional.

### Password protection

Supabase Auth tiene desactivada la protección de contraseñas filtradas. Conviene habilitarla desde la configuración de Auth después de revisión. No se cambió porque sería una modificación directa de producción.

### RLS/performance

Advisor reporta políticas permisivas superpuestas en varias tablas y 43 índices todavía sin uso. La base tiene muy poco volumen operativo, por lo que “unused” no es evidencia suficiente para borrar índices. Consolidar policies puede hacerse en un PR separado con pruebas por rol.

### Integridad de costos en entradas/devoluciones

`record_entry` y `record_return` aceptan costo/moneda enviados por el cliente para crear lotes FIFO. El frontend también permite capturarlos en entradas/devoluciones.

Esto puede ser correcto si el depositario está autorizado a registrar costo real, pero también permite que un usuario de depósito altere valorización si se equivoca o manipula la petición. No se cambió porque requiere una decisión de negocio: costo solo administración, costo heredado del movimiento de salida, o lote sin valorar hasta revisión.

### Deriva entre repositorio y producción

La historia de migraciones en Supabase no coincide exactamente en timestamps/nombres con los archivos del repositorio (por ejemplo, la migración de inteligencia de compras aparece aplicada en producción con una versión distinta al nombre del archivo GitHub). Además, varias Edge Functions administrativas desplegadas todavía no están versionadas en V3.

Esto no es un fallo inmediato de ejecución, pero reduce reproducibilidad y recuperación ante incidentes. Debe normalizarse sin reescribir migraciones ya aplicadas.

### Alcance legacy

V3 declara contratistas/liquidaciones fuera del producto activo. Sin embargo, algunas funciones desplegadas de exportación y el asistente de compras todavía consultan datos históricos de contratistas. No se eliminó porque podría afectar reportes existentes; conviene decidir si se conserva como lectura histórica o se retira explícitamente.

## Cambios de esta rama

1. `src/core/auth.js`: cierre de sesión resistente a refresh.
2. `src/core/router.js`: solicitud de productos coherente por rol.
3. `migrations/20260921172000_receipt_document_path_guard.sql`: vínculo seguro archivo ↔ compra/recepción.
4. `edge-functions/avh-admin-recover/index.ts`: recuperación administrativa endurecida y versionada.
5. `edge-functions/avh-admin-temp-reset/index.ts`: endpoint temporal retirado.
6. `scripts/check.mjs`: contratos automáticos para impedir regresiones de estos fixes.

## Qué debe ocurrir después de aprobar el PR

Este PR **no despliega cambios de base ni Edge Functions**. Después de revisión explícita:

1. aplicar la migración de guardia de documentos en un entorno controlado y luego producción;
2. desplegar la versión endurecida de `avh-admin-recover`;
3. retirar/desplegar como 410 `avh-admin-temp-reset`;
4. habilitar leaked-password protection en Supabase Auth;
5. ejecutar nuevamente Security/Performance Advisors;
6. hacer una prueba de roles: admin, depositario de depósito A y depositario de depósito B;
7. reconciliar el inventario de Edge Functions y migraciones entre GitHub y Supabase.
